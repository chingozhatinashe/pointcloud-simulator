# Data Component

## Overview

The Data component is responsible for ingesting, preprocessing, and managing all point cloud data in the pipeline — both real LiDAR scans and synthetic datasets generated by the Simulator. Its primary responsibility is to produce `FloorPointCloud` objects in the canonical format defined by the Representation component, so that the Inference component and Simulator can operate on real and synthetic data interchangeably.

The component sits between the raw world of LiDAR file formats and the clean mathematical world of the rest of the pipeline. Its job is to absorb all the messiness of real data — varying file formats, coordinate frames, noise characteristics, missing floors, and inconsistent scan densities — and present a uniform interface to everything downstream.

The Data component has no dependency on the Simulator or Inference components. It depends only on the Representation component for the `FloorPointCloud`, `PointCloudSlice`, `Building`, and `FloorPlanGraph` data structures.

---

## Language and Libraries

**Primary language:** Python 3.11+

**Core libraries:**

- `laspy` — reading and writing `.las` and `.laz` files, the dominant real-world LiDAR format
- `open3d` — reading `.ply` and `.pcd` files; point cloud downsampling, normal estimation, and visualisation utilities
- `numpy` — array manipulation during preprocessing; all intermediate processing uses numpy before conversion to JAX arrays
- `JAX` — final conversion of preprocessed arrays to `jnp.ndarray` for consumption by Simulator and Inference
- `dataclasses` — dataset metadata containers
- `pathlib` — file and directory management
- `json` — metadata serialisation for synthetic datasets
- `h5py` — storage format for large synthetic datasets of `(G, D)` pairs generated for SBI training

**Optional libraries (for specific benchmark datasets):**

- `plyfile` — low-level `.ply` parsing for ScanNet and Matterport3D formats
- `trimesh` — mesh-to-point-cloud conversion where benchmark datasets provide meshes rather than raw scans

## Core Responsibilities

### 1. Real Scan Ingestion

Load raw LiDAR scan files from disk and convert them to `FloorPointCloud` objects. This is the primary interface between the real world and the pipeline.

**Supported input formats:**

- `.las` / `.laz` — standard terrestrial LiDAR survey format; most real building scans will arrive in this format
- `.ply` — common in academic benchmark datasets (ScanNet, Matterport3D, S3DIS)
- `.pcd` — Point Cloud Data format used by ROS and some scanner manufacturers
- `.e57` — ASTM standard for 3D imaging data; used by professional survey-grade scanners (Leica, FARO)

**Loading pipeline:**

For each file, the loader must:

1. Read raw 3D points as an `(N, 3)` array in the file's native coordinate frame
2. Extract any available metadata — scanner position, scan date, point intensity, return number
3. Apply coordinate frame normalisation (see §3)
4. Pass the normalised point cloud to the preprocessing pipeline (see §4)
5. Return a `FloorPointCloud`

**Scanner position extraction:**

Where the file format encodes scanner positions (as is common in `.e57` and some `.las` files), these must be extracted and stored in `FloorPointCloud.scanner_positions`. Where scanner positions are not encoded in the file, they should default to `None` and a warning should be logged — some inference approaches require scanner positions and will need them provided separately.

### 2. Synthetic Dataset Management

Manage large collections of `(FloorPlanGraph, FloorPointCloud)` pairs generated by the Simulator for SBI training and benchmarking.

**Generation interface:**

Provide a `DatasetGenerator` class that wraps the Simulator and handles the logistics of generating large datasets:

- Accept a `FloorPlanPrior` (from the Inference component) to sample random floor plans `G ~ P(G)`
- Accept a `NoiseModelPrior` to sample noise parameters per simulation call (domain randomisation)
- Call the Simulator for each `(G, noise_model)` pair
- Store results incrementally to disk using `HDF5` via `h5py` — never accumulate the full dataset in memory
- Support resuming interrupted generation runs

**Storage format:**

Synthetic datasets are stored as HDF5 files with the following structure:

```
dataset.h5
├── metadata/
│   ├── n_samples          # total number of (G, D) pairs
│   ├── simulator_version  # hash of simulator config used
│   ├── noise_prior        # serialised NoiseModelPrior parameters
│   └── floor_plan_prior   # serialised prior parameters
├── floor_plans/
│   ├── segments/          # (n_samples, K_max, 4) — padded segment arrays
│   ├── junctions/         # (n_samples, J_max, 2) — padded junction arrays
│   ├── segment_masks/     # (n_samples, K_max) — validity masks
│   └── junction_masks/    # (n_samples, J_max) — validity masks
└── point_clouds/
    ├── points_3d/         # ragged array — (n_samples,) of (N_i, 3) arrays
    ├── slice_heights/     # (n_samples, H) — heights used per sample
    └── scanner_positions/ # (n_samples, M, 2)
```

**Loading interface:**

Provide a `SyntheticDataset` class that:

- Wraps an HDF5 file and exposes it as an iterable of `(FloorPlanGraph, FloorPointCloud)` pairs
- Supports random access by index for batch sampling during training
- Supports train/validation/test splitting by index range
- Loads data lazily — reads from disk on demand rather than loading the full dataset into memory

### 3. Coordinate Frame Normalisation

Real LiDAR scans arrive in arbitrary coordinate frames — GPS coordinates, scanner-local frames, or site-specific survey frames. The pipeline requires a consistent coordinate frame:

- **Origin** — translated so that the bounding box minimum corner is at `(0, 0, 0)`
- **Scale** — coordinates in metres; convert from any other unit if necessary
- **Orientation** — Z axis pointing up; rotate if the scan is in a different convention
- **Storey alignment** — Z coordinate represents height above floor level of the lowest storey

**Normalisation pipeline:**

```
Raw points (arbitrary frame)
        ↓
Unit detection and conversion to metres
        ↓
Rotation to Z-up convention
        ↓
Translation to (0, 0, 0) origin at bounding box minimum
        ↓
Normalised points (pipeline coordinate frame)
```

The normalisation transform must be stored alongside the data so that results can be mapped back to the original coordinate frame if needed.

### 4. Preprocessing

Transform a normalised raw 3D point cloud into a `FloorPointCloud` with clean height slices ready for inference.

**Storey segmentation:**

Partition the full building point cloud into per-storey point clouds by analysing the Z-axis point density histogram. Peaks in the histogram correspond to floor and ceiling surfaces; the valleys between them define storey boundaries. This must handle:

- Standard single and multi-storey buildings
- Varying inter-storey heights across floors
- Missing data at storey boundaries (incomplete ceiling scans)

Each detected storey produces an independent `FloorPointCloud` for inference.

**Height slice extraction:**

Given a storey point cloud and a list of target heights `{h_i}`, extract the subset of points within a configurable tolerance `δh` of each target height:

```
P_i = {p ∈ P : |p_z - h_i| < δh}
```

Default `δh = 0.05m`. The tolerance is configurable — tighter tolerances give cleaner slices but fewer points; wider tolerances give denser slices with more clutter from non-wall surfaces.

**Outlier removal:**

Remove statistical outliers from each slice using a nearest-neighbour distance threshold. Points whose mean distance to their k nearest neighbours exceeds a configurable threshold are flagged as outliers and removed. This is applied per slice after height extraction.

**Downsampling:**

Real scans can contain tens of millions of points — far more than inference requires. Apply voxel grid downsampling per slice to reduce to a manageable density. Default voxel size `0.02m`. The target density should be configurable to match the density of synthetic data from the Simulator, reducing the sim-to-real gap at the data level.

**Bounding box computation:**

Compute and store `floor_plan_bounds` — the 2D bounding box `(x_min, y_min, x_max, y_max)` of the full storey point cloud. This is used by the Simulator and Inference components to define the spatial domain.

### 5. Benchmark Dataset Wrappers

Provide standardised loaders for established academic datasets that contain building point clouds with ground truth annotations. These are used for evaluating inference quality against known floor plans.

**Supported datasets:**

**ScanNet** — indoor RGB-D scans with mesh reconstructions. Loader converts mesh to point cloud via surface sampling, extracts per-room annotations, and constructs approximate ground truth `FloorPlanGraph` objects from the provided 2D floor plan annotations.

**Matterport3D** — high-quality panoramic RGB-D scans of residential and commercial buildings. Loader handles the Matterport coordinate convention and extracts room-level segmentation.

**S3DIS (Stanford Large-Scale 3D Indoor Spaces)** — annotated point clouds of office buildings across 6 areas. Loader extracts wall point annotations to construct approximate ground truth `FloorPlanGraph` objects.

**Interface contract:**

Every benchmark wrapper must expose the same interface:

```python
class BenchmarkDataset(Protocol):
    def __len__(self) -> int: ...
    def __getitem__(self, idx: int) -> tuple[FloorPointCloud, FloorPlanGraph | None]: ...
    def split(self, ratio: tuple[float, float, float]) -> tuple[Self, Self, Self]: ...
```

The `FloorPlanGraph | None` return type reflects that ground truth floor plans are available in some datasets but not all — the wrapper returns `None` where ground truth is unavailable.

---

### 6. Data Validation

Provide utilities to verify that loaded and preprocessed data meets the expectations of the pipeline before it is passed to inference.

**Checks to implement:**

- Minimum point count per slice — warn if any slice has fewer than a configurable threshold of points (default 50); very sparse slices produce unreliable likelihoods
- Coordinate frame sanity — verify all points lie within the declared `floor_plan_bounds`; flag points outside the bounding box
- Slice consistency — verify that the same dominant wall positions appear consistently across height slices; large inconsistencies may indicate a coordinate frame error or a poorly segmented storey
- Scanner position plausibility — if scanner positions are available, verify they lie inside the floor plan bounding box

Validation results are returned as a structured `ValidationReport` dataclass listing warnings and errors, not raised as exceptions — the caller decides whether to proceed with imperfect data.

## Key Design Constraints

**Format parity between real and synthetic data.** The output of every loader and the output of the Simulator must be identical `FloorPointCloud` objects. Inference code must never need to branch on whether data is real or synthetic. This is a hard interface requirement.

**Lazy loading for large datasets.** SBI training datasets can contain millions of `(G, D)` pairs and will not fit in memory. The `SyntheticDataset` class must load from HDF5 lazily. Never load a full dataset into memory.

**Preprocessing is configurable and logged.** Every preprocessing decision — voxel size, slice tolerance, outlier threshold — is a parameter that affects inference quality. All parameters must be explicit, configurable, and logged alongside results so that experiments are reproducible.

**No inference logic here.** The Data component transforms raw data into the pipeline's canonical format. It does not make decisions about which slices are informative, weight slices differently, or compute likelihoods. Those decisions belong to the Inference component.

**Coordinate frame normalisation is invertible.** The normalisation transform must be stored so that inferred floor plans in pipeline coordinates can be mapped back to the original survey coordinate frame for downstream use.

## Out of Scope

- Point cloud registration — aligning multiple scans from different scanner positions into a single coordinate frame (assumed to be done by the survey workflow before data reaches this pipeline)
- RGB or intensity data — points carry 3D position only; colour and intensity channels are discarded on load
- Mesh reconstruction — the pipeline works directly with point clouds; mesh intermediate representations are not used
- Streaming or real-time ingestion — all data is loaded from files; live scanner feeds are out of scope
- Data augmentation for neural training — augmentation (rotation, scaling, jitter) is handled by the Inference component's training loop, not here
